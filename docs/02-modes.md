# 阶段二：用模式组织教学

先看 `prompts.py`。三种模式共享中文表达、承认未知和能力边界，再各自增加教学要求。

- 代码导师：解释概念、给最小示例，练习时逐级提示。
- 论文阅读：只根据提供文本分析，区分原文、推断和背景知识。
- 复习教练：一次一题，等待用户回答后反馈。

这三个模式仍使用同一个模型服务。用户选模式，服务端根据保存的 `mode` 选择系统提示词，前端不能任意提供 system 消息。提示词引导输出，但不能保证每次回答都正确，特别是论文事实仍需核对原文。

## 系统提示词和历史不同

系统提示词定义角色和规则。历史消息记录“用户说了什么、助手答了什么”。`routes.py` 中的 `prepare()` 每次把它们组合：system + history + 当前 user。

保存文件只有 user/assistant 消息，system 不作为聊天记录保存。修改提示词会影响下一次请求，而不需要批量改历史文件。会话内上下文来自历史消息的再次发送，不代表模型自动拥有永久记忆。

## 会话数据为什么增加字段

新格式包含 `version`、`id`、`mode`、`name`、`custom_name`、时间和 `messages`。
`version` 用于识别格式；`custom_name` 防止用户自己的名称被自动标题覆盖。标题取第一条成功消息的前 28 个字符，压缩换行后生成，不额外请求模型。

旧格式由读取层转成统一的展示结构：名称为“历史字谜会话”，模式为 legacy，只读。转换发生在内存中，不会回写文件。这样新代码能展示旧数据，也不会把原来的字谜对话混入代码学习。

模式在创建时确定，修改接口只允许 name。你需要切换教学任务时，新建会话即可。

## 前后端接口是一份约定

列表原来只有 ID，现在返回摘要对象。`static/app.js` 用摘要显示名称、模式和日期；打开会话才请求完整消息。这是“列表摘要”和“详情”各自承担职责的例子。

服务端用 URL 中的 ID 定位会话。旧客户端如果还传 body.session_id，必须一致，否则拒绝，避免“路径说改 A，正文却说改 B”的歧义。

## 自己验证

分别创建三种会话，刷新后重新打开，检查模式和名称。手动改名后发送第一条消息，名字不应被覆盖。打开旧字谜记录，输入框和重命名应不可用，但可以查看或删除。

可选练习：在代码导师提示词中增加“解释循环时优先用列表例子”，重启后问一个循环问题。观察不同问题下效果的变化，并想想为什么这不是一个保证输出完全一致的程序分支。
