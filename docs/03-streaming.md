# 阶段三：流式回复与页面状态

普通请求会等模型答完再返回。流式请求允许模型产生一段正文，后端就向浏览器发送一段。因此用户更早看到进展，但程序要处理“还没完成”的状态。

## 先理解 async、await、yield

`async def` 定义协程。遇到网络等待时，`await` 让当前任务暂时让出执行机会，服务还可以处理别的请求；它不意味着所有 Python 计算都自动并行。

`llm.py` 的 `stream()` 同时含有 `async def` 和 `yield`，因此是异步生成器。每次 `yield` 交出一个正文片段；路由用 `async for` 逐段消费，再编码成 SSE 事件。

`delta` 表示正文片段，`done` 表示正文完整且已保存，`error` 表示出错。只收到一些 delta 不算成功。模型的内部推理字段不会传给页面，也不会保存。

## 为什么收到一块数据不能马上 JSON.parse

网络可能把一个 SSE 帧切成多块，也可能把多个帧放在同一块里；一个汉字的 UTF-8 字节也可能被拆开。

`static/stream.js` 先用 TextDecoder 的 stream 模式处理跨块字符，再累积字符串，按空行分离完整事件，最后解析事件里的 JSON。可以用 `node --test tests/frontend.test.cjs` 看“逐字节传输中文”的测试。

## 页面状态比 DOM 更重要

`static/app.js` 用 Map 按会话 ID 分别保存历史、草稿和生成状态。DOM 是状态的展示结果，不是唯一数据来源。响应必须先更新所属会话的数据，只有当前正在看它时才更新对话区。

`loadVersion` 用来识别旧的加载请求：先点 A 再点 B，如果 A 比 B 更晚返回，A 的结果不能把 B 页面覆盖。`busy` 则在第一次 await 前设置，阻止快速双击产生两次生成请求。

回复失败时，页面显示“未完成”，恢复草稿。服务器仅在回答完整后保存一轮消息。若服务器已经提交但完成通知丢失，页面查询历史确认，避免直接重试重复保存。草稿只在页面内存里，刷新会丢失。

## Markdown 为什么不能直接塞进 innerHTML

回答文本可能包含脚本、事件属性或恶意链接，即使来源是模型也不能信任。页面先用 Marked 解析 Markdown，再用 DOMPurify 清洗 HTML，最后插入 DOM 并添加高亮和复制按钮。原始用户消息始终用 textContent 展示。

外部图片和媒体不渲染，避免一段回答自动加载第三方资源；普通安全链接仍可点击。清洗后的代码块由 Highlight.js 高亮。

## 自己验证

发送一段要求代码示例的问题，观察逐段回复并复制代码。生成期间切到另一段会话，再返回确认回答没有串线。输入中文时按回车选词不应发送；Shift+Enter 应换行。

浏览器自动检查使用 `npm.cmd run test:browser`，服务和模型都是临时模拟环境，还会检查脚本注入、失败重试及窄屏布局。

可选练习：阅读 `readSSE()`，解释为什么 finally 中要释放 reader；再把示例中的一个中文字符拆成两个字节块，观察 TextDecoder 在启用和关闭 stream 时的区别。
